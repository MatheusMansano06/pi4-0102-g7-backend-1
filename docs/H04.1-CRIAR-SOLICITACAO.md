# H04.1 criação de solicitação

POST /api/solicitacoes do #1145 integrado parcialmente na main pela PR #14,
merge 6181761, por autorização do Luis. Esta revisão do #1136 corrige a
especificação e configura o banco para a regra agora confirmada: **dimensão e
diâmetro permitidos e opcionais para todos os materiais do MVP**.

A definição dos campos é do Luis, não uma tarefa pendente de a Lara descobrir.
O [dicionário](especificacao/colunas-materiais-e-solicitacoes.md) fixa os seis
nomes/tipos, nulabilidade, defaults, unidades e capacidade de texto. Lara/H01.2
recebe a especificação e coordena a aplicação no banco existente.

## Identidade confiável

O controller recebe request attribute interno usuarioAutenticado, do tipo
[UsuarioAutenticado](../src/main/java/com/archflow/comum/UsuarioAutenticado.java),
com usuarioId de domínio e perfil. H02.2/Matheus deve fornecê-lo após validar
Keycloak e resolver o vínculo com o usuário. Não copiar headers livres para ele,
decodificar token sem validar ou converter nome de Principal genérico em aluno.

Sem contexto, corpo válido recebe 401 NAO_AUTENTICADO; perfil não ALUNO recebe
403 ACESSO_NEGADO. JSON, X-Perfil e X-Usuario-Id não autenticam. A integração ainda
não produz esse contexto. Testes o injetam como fixture e não provam Keycloak.
Binding ilegível pode retornar 400 antes do serviço; precedência do filtro real
será conferida em H02.2. Não criar autenticação fictícia para liberar o POST.

## Operação e resultado

Entrada: materialId inteiro positivo, quantidade inteira positiva, dimensao
textual opcional, diametro numérico positivo/finito opcional e observacao textual
opcional. Nenhum campo adicional é aceito, incluindo usuarioId/status/dataLimite.
Ver [CT03](contratos/CT03-criarSolicitacao.md) e [CT12](contratos/CT12-consultar%20e%20persistir%20solicita%C3%A7%C3%B5es.md).

Servidor associa aluno, cria PENDENTE e horários iguais inicialmente; transação
com saveAndFlush confirma a gravação. HTTP 201 devolve solicitacaoId, materialId,
quantidade, status, criadaEm, dimensao, diametro e observacao da entidade salva.
Preserva medidas ao alterar status/previsão e não baixa/reserva saldo ou gera avisos.

A API não analisa largura/altura dentro do texto dimensao. A tela deve compô-lo
em mm na integração. A entrada limita dimensão/observação a 255 pela contagem
String.length(), recusa excesso com 400 DADOS_INVALIDOS antes de gravar e
preserva o texto permitido sem corte/trim. Ausência/null continuam opcionais.
DOUBLE PRECISION acompanha Double,
sem escala decimal fixa. dataLimite não foi definida e permanece fora da entrada.

## Política e scripts agora definidos

aceita_dimensao=TRUE, exige_dimensao=FALSE, aceita_diametro=TRUE e
exige_diametro=FALSE para todos, inclusive materiais inativos que continuam
bloqueados pela regra de ativo. Pode solicitar com uma, duas ou nenhuma medida.
NULL/incoerência ainda retorna 503 CONFIGURACAO_PENDENTE, sem INSERT; não é
sinônimo de regra opcional. A configuração precisa existir no banco do destino.

- [01-tabelas.sql](../banco/01-tabelas.sql): seis colunas; quatro defaults
  correspondentes à decisão do Luis; NULL explícito ainda pode indicar falha.
- [02-dados-exemplo.sql](../banco/02-dados-exemplo.sql): seis materiais configurados
  explicitamente com essa regra, sem alterar saldos/ativo ou os pedidos de exemplo.
- [Atualização](sql/H04.1-colunas-propostas.sql): adiciona colunas, configura defaults
  e atualiza só os quatro indicadores de todos os materiais. É uma transação,
  pode repetir e não altera saldo/pedidos/datas. A antiga ausência de UPDATE foi
  substituída pela configuração expressamente confirmada pelo Luis.

Arquivo em docs/sql não roda automaticamente no Docker. Volume existente precisa
receber a atualização antes de iniciar a API com validate, sem apagar dados.
Tipos incompatíveis já existentes não são corrigidos por IF NOT EXISTS.
Não houve aplicação no banco compartilhado. Compose mantém credenciais de banco
/API vindas do mesmo .env; mudar env não altera senha de banco inicializado.

## Erros

| Situação | HTTP / código |
| --- | --- |
| Sem identidade validada | 401 NAO_AUTENTICADO |
| Perfil não ALUNO | 403 ACESSO_NEGADO |
| Corpo/campo/materialId inválido | 400 DADOS_INVALIDOS |
| Quantidade inválida | 400 QUANTIDADE_INVALIDA |
| Material inexistente/inativo | 404 MATERIAL_NAO_ENCONTRADO |
| Medida inválida/incompatível com configuração | 400 PARAMETROS_INVALIDOS |
| Configuração NULL/incoerente | 503 CONFIGURACAO_PENDENTE |
| Falha de persistência | 500 ERRO_INTERNO |

## Evidência e limites

Na integração da PR #14, 67 testes padrão passaram; quatro PostgreSQL
condicionais ficaram desabilitados nessa suíte. Separadamente, os quatro testes
PostgreSQL passaram em instalação nova e em cópia migrada (oito execuções), com
preservação de dados e consulta no histórico do aluno correto. Esses resultados
precedem a política uniforme/defaults desta revisão e não provam sua aplicação
no destino. Evidência nova fica na descrição da PR #10.

Para repetir PostgreSQL, criar banco dedicado com prefixo archflow_ct03_teste_
e configurar ARCHFLOW_CT03_TESTE_URL, ARCHFLOW_CT03_TESTE_USUARIO e
ARCHFLOW_CT03_TESTE_SENHA só no processo. Executar SolicitacaoCriacaoBancoTest.
Os cinco testes usam transação/rollback, repositórios reais e identidade de fixture;
não apontar para banco compartilhado. Configuração mantém validate.
