## Identidade: integração com H02.2, sem autenticação fictícia

O controller recebe um atributo interno da requisição chamado `usuarioAutenticado`,
do tipo [UsuarioAutenticado](../src/main/java/com/archflow/comum/UsuarioAutenticado.java).
Esse objeto contém usuarioId de domínio e perfil; é um ponto de integração a
revisar com o Matheus, não uma implementação do login Keycloak.

Após validar Keycloak e resolver o vínculo com o usuário do ArchFlow, a camada
de autenticação deve fornecer esse contexto internamente à requisição. Não basta
decodificar um token sem validar ou converter o identificador do provedor em Long.
Não criar um filtro provisório que copie os valores de cabeçalhos do cliente.

O POST não lê X-Perfil, X-Usuario-Id ou um usuarioId livre do JSON como identidade.
Também não transforma o nome de um Principal genérico em identificador de aluno.
Sem o contexto validado, um corpo válido retorna 401 NAO_AUTENTICADO; perfil
RESPONSAVEL retorna 403 ACESSO_NEGADO. O contexto só pode ser preenchido pelo
servidor; não existe um campo JSON ou cabeçalho HTTP que o crie.

**Estado atual:** H02.2 ainda não produz esse contexto. Logo, uma chamada HTTP
comum não cria pedidos nesta branch só por enviar um Bearer ou X-Perfil. Os testes
injetam uma identidade de fixture pelo MockMvc; não comprovam Keycloak nem #1141.
Corpos ilegíveis podem ser recusados pelo binding MVC com 400 antes da operação;
a precedência de autenticação no filtro real será validada na integração H02.2.

## Entrada e resultado

Campos aceitos: materialId, quantidade, dimensao, diametro e observacao.

```json
{
  "materialId": 7,
  "quantidade": 2,
  "dimensao": "300 x 200 mm",
  "diametro": 4.5,
  "observacao": "Separar para a maquete"
}
```

O exemplo é uma fixture para um material de teste que aceite ambos os parâmetros.
Não define a política de nenhum material real nem aprova mm como unidade oficial.

- materialId: inteiro positivo. Frações, texto, booleanos e estouro de Long são recusados.
- quantidade: inteiro positivo, sem arredondar fração ou converter texto.
- dimensao: texto opcional conforme material, preservado como recebido; texto
  informado somente com espaços é recusado. O formato e a unidade ainda serão
  definidos com o grupo; não há parse de largura/altura ou conversão cm/mm.
- diametro: número JSON positivo e finito quando informado; não aceita texto com
  unidade. Double é a proposta técnica atual; precisão de negócio segue pendente.
- observacao: texto opcional, preservado. Não são impostos limites de negócio inventados.
- Campos desconhecidos são recusados com DADOS_INVALIDOS: inclusive usuarioId,
  perfil, status, criadaEm, atualizadaEm e a dataLimite ainda não definida.

Sucesso proposto: HTTP **201**, com solicitacaoId, materialId, quantidade, status,
criadaEm, dimensao, diametro e observacao. Os dados retornados vêm da entidade
gravada, não do eco do JSON. Aluno, PENDENTE e datas são definidos no servidor.
O construtor inicializa criadaEm e atualizadaEm com o mesmo instante.

O serviço exige material existente e ativo, valida as regras e grava com
saveAndFlush dentro de transação. Não faz baixa/reserva automática do estoque,
não inventa recusa por saldo insuficiente e não cria notificações; esses efeitos
não foram definidos para este recorte.

## Regras por material: proposta técnica, sem defaults de negócio

| Atributo em Material | Coluna proposta | Significado |
| --- | --- | --- |
| aceitaDimensao | aceita_dimensao | Pode receber dimensão |
| exigeDimensao | exige_dimensao | Deve receber dimensão |
| aceitaDiametro | aceita_diametro | Pode receber diâmetro |
| exigeDiametro | exige_diametro | Deve receber diâmetro |

Os quatro indicadores são Boolean **anuláveis**. Um null significa que a regra
ainda não foi definida; não equivale a false. O POST retorna 503
CONFIGURACAO_PENDENTE sem inserir pedido quando algum valor falta ou uma regra
exige algo que não aceita. Quatro valores false permitem pedido sem medidas,
mas precisam ser uma decisão explícita, não um default para dados existentes.

Quando a política está completa, parâmetro não aceito ou obrigatório ausente
retorna 400 PARAMETROS_INVALIDOS. Dois parâmetros podem coexistir somente quando
ambos são aceitos. Os indicadores não são inferidos de nome, especificacao ou regex.

Esta é uma proposta física simples para revisão com a Lara, diferente das listas
parametrosAceitos/parametrosObrigatorios propostas no JSON da PR #10. Não foi
alterado o DTO do catálogo para expor essas listas; alinhar essa projeção com o
frontend antes de #1147. Nenhum cadastro de política real foi feito neste trabalho.

## Erros da operação

| Situação | HTTP | Código |
| --- | --- | --- |
| Contexto de identidade validada ausente | 401 | NAO_AUTENTICADO |
| Perfil diferente de ALUNO | 403 | ACESSO_NEGADO |
| JSON/campos inválidos ou campo ainda não definido | 400 | DADOS_INVALIDOS |
| Quantidade ausente, não inteira ou não positiva | 400 | QUANTIDADE_INVALIDA |
| Material inexistente ou inativo | 404 | MATERIAL_NAO_ENCONTRADO |
| Medida inválida, não aceita ou obrigatória ausente | 400 | PARAMETROS_INVALIDOS |
| Política do material não configurada/inconsistente | 503 | CONFIGURACAO_PENDENTE |
| Falha inesperada de gravação | 500 | ERRO_INTERNO |

O formato continua sendo codigo/mensagem. Falha de gravação não devolve sucesso
nem detalhes internos. Nenhuma dependência nova foi adicionada; reutilizam-se
Spring MVC/JPA/JUnit já presentes e classes, wrappers, interfaces e exceções do
material da disciplina. O SQL proposto e a integração de contexto são itens para
revisão, não decisões acadêmicas já validadas.

## Verificação e reprodução

`mvn test` executa as regras e testes HTTP, além da suíte existente. A classe
SolicitacaoCriacaoBancoTest fica desabilitada sem configuração explícita de banco:
isso mantém a CI atual independente de um PostgreSQL externo.

Para os testes com PostgreSQL, preparar um **banco novo e dedicado** cujo nome
comece com archflow_ct03_teste_, usando o SQL da PR #12 ac646019 e a proposta de
colunas. Configurar somente no processo de teste:

- ARCHFLOW_CT03_TESTE_URL: URL JDBC desse banco dedicado.
- ARCHFLOW_CT03_TESTE_USUARIO: usuário local com acesso ao banco de teste.
- ARCHFLOW_CT03_TESTE_SENHA: credencial local, fora do Git e de mensagens.

Executar `mvn -Dtest=SolicitacaoCriacaoBancoTest test`. Os três testes usam a API
via MockMvc, serviço e JPA reais: criação e nova leitura com EntityManager limpo;
mudança de status preservando parâmetros; política pendente sem INSERT.
Cada teste desfaz sua transação e não cria/apaga tabelas. A configuração mantém
ddl-auto: validate. O teste não deve apontar para banco real de usuários.

O contexto de aluno e as políticas ainda são fixtures, mesmo com PostgreSQL real.
Isso valida persistência da proposta, não fecha autenticação, implantação do SQL
oficial ou integração de tela #1147. Não reativa a etapa cancelada da PR #9.
